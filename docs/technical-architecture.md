# المعمارية التقنية

## قرار البناء

المنصة **Modular Monolith**: واجهة React مستقلة، وواجهة API وخدمات تطبيقية وعمال مهام في مستودع واحد. تنشر نسخ API stateless خلف موازن حمل، ويشترك العمال معها في PostgreSQL. حدود الوحدات تحافظ على فصل الـDomain عن مزودي Meta وMessaging وPayment وEmail وAI وGoogle. لا توجد خدمة خارجية تصبح مصدر الحقيقة التشغيلية.

الاختيارات:

| الطبقة | الاختيار | السبب |
|---|---|---|
| اللغة | TypeScript على Node.js 24 | أنواع مشتركة، نظام حزم واحد، ودعم محلي متوفر |
| API | Fastify مع JSON Schema validation | حدود HTTP واضحة، تحقق مدخلات وأداء ملائم |
| الواجهة | React وVite | واجهة متعددة اللغات والشاشات مع تحميل تدريجي |
| قاعدة البيانات | PostgreSQL | معاملات وقيود وفهارس و`FOR UPDATE SKIP LOCKED` للتزامن |
| الوصول للبيانات | SQL parameterized عبر `postgres` | استعلامات وصلاحيات وفهارس صريحة وقابلة للمراجعة |
| المهام | جدول PostgreSQL durable jobs وoutbox | ذرية كتابة الحالة والنية داخل معاملة واحدة؛ لا يعتمد قبول Webhook على Redis |
| المصادقة | Argon2id وsession cookie عشوائية مخزنة hash | إبطال الجلسات وربطها بحالة الحساب، دون JWT طويل الأجل |
| الأسرار التشغيلية | AES-256-GCM بمفتاح deployment منفصل | إدارة Connections داخل المنصة دون إظهار السر بعد حفظه |
| الملفات | Object storage adapter؛ تخزين محلي معزول للتطوير | تحكم الوصول وفحص النوع والحجم وإمكان استبدال التخزين |

Docker Compose يوفر PostgreSQL للتطوير وبيئات الاختبار. تحقق تشغيل PostgreSQL 18 محلياً وتطبيق migrations واختبارات API عليه. لا يُستخدم SQLite كبديل إنتاج صامت.

## حدود الوحدات

`identity`, `organization`, `campaigns`, `fields`, `leads`, `routing`, `conversations`, `messaging`, `integrations`, `ai`, `followups`, `payments`, `analytics`, `automations`, `imports`, `notifications`, `audit`. واجهات HTTP تستدعي application services؛ adapters وحدها تتحدث إلى الخارج. يشترك كل مسار قراءة/تعديل في authorization service، وتُفلتر الصفوف في SQL حسب branch/owner قبل الإرجاع أو export أو AI tool.

## مرفقات Messaging الواردة

`message_attachment` هو سجل metadata دائم مرتبط بـ`integration_event`، ويمكن إلحاقه بـMessage واحدة فقط. المحتوى والتعليق التاريخيان لا يتغيران؛ migration `031` توسع حماية Message لتشمل معرّف المرفق وتحمي هوية المرفق وبيانات المحتوى بعد `READY`. يحفظ inbound resolver المرفق قبل حلّ الغموض، ويلحق الرسالة عند تطابق Conversation/Lead واحد وفق القواعد السابقة؛ لا تحتاج المطابقة إلى انتهاء التنزيل أو الفحص. المرفق الملتبس يبقى متاحاً لمراجعي Connection فقط حتى الحسم، ثم يرث Lead access الحالية، بما فيها خسارة Agent السابق صلاحية التحميل بعد إعادة الإسناد.

عامل `media-worker` مستقل حتى لا تؤخر HTTP media أو ClamAV عامل الرسائل النصية/Callbacks. يلتقط صفاً بـ`SKIP LOCKED`، ويثبت lease لمدة خمس دقائق ورمز fencing وتاريخ المحاولات قبل I/O خارج المعاملة. التنزيل عملية قراءة قابلة لإعادتها بعد crash، بخلاف customer send ذي النتيجة المجهولة؛ المحاولة القديمة لا تستبدل نتيجة lease جديدة. خمس محاولات مع backoff bounded؛ انتهاء المحاولات يبقي `FAILED` وسجلها، وتتيح UI إعادة دورة معالجة صريحة مدققة بـversion وسبب لمسؤولي النطاق فقط. `REJECTED` لا يتيح تجاوز الرفض أو تحويل الملف إلى جاهز يدوياً. تعطيل Sender/Connection أو تجاهل الحدث يمنع التقاطه ولا يفقد السجل.

Meta media adapter يطلب metadata مع `phone_number_id` ثم يحمل bytes بواسطة credential المخزنة مشفّرة. لا يستخدم URL أو filename من Webhook كمسار تخزين. لا يتبع redirects ولا يرسل token إلى host غير `https://lookaside.fbsbx.com`؛ اختلاف host يحتاج تحديث adapter واختباره بعد التحقق من مواصفات المزود. الاستجابة bounded حتى مع غياب `Content-Length`، وmetadata محدودة ومهل HTTP صريحة. الحجم التقني الافتراضي 25 MiB، قابل للتعديل عبر `MEDIA_MAX_BYTES` بين 1 KiB و100 MiB؛ ليس ادعاءً عن حد تجاري للمزود. أنواع هذا المسار: JPEG/PNG، PDF، OGG/MP3/M4A، MP4 وWebP sticker. الأنواع الأخرى تُحفظ كأحداث للمراجعة دون ادعاء دعمها. `file-type` يحدد النوع من bytes، ويجب أن يطابق النوع المسموح والبصمة SHA-256 الواردة الموقعة؛ detection ليس بديلاً عن scanning.

ClamAV adapter يستخدم `INSTREAM` لا filesystem path، ويرفض scanner غير متاح أو definitions أقدم من سبعة أيام أو رد غير كامل. إعداد Compose يفعل رفض المحتوى المشفر وتجاوز حدود الفحص، ولا يُنشر TCP خارج localhost. نجاح الفحص وحده يسبق تخزين bytes وإتاحة التحميل. التخزين adapter خاص: Local للتطوير بملفات وأسماء UUID/hash وatomic writes خارج web root، أو S3-compatible bucket خاص للنسخ الإنتاجية المشتركة مع AWS SDK وdeployment credentials صريحة. يجب اختيار backend صراحة في production؛ لا fallback صامت إلى Local. لا يوجد public URL أو presigned URL يتجاوز session/Lead ACL. API يعيد فحص صلاحية الوصول والبصمة والحجم عند كل تحميل، ويستخدم `attachment` و`octet-stream` و`nosniff` و`no-store` واسم ملف مولداً، ويحفظ Audit دون bytes أو أسرار. الواجهة تعرض التعليق كنص React وحالة الفحص وزر التحميل/إعادة المعالجة؛ لا inline rendering لملفات غير موثوقة.

المراجع التقنية: [Meta media retrieval](https://www.postman.com/meta/whatsapp-business-platform/request/fpj02x0/retrieve-media-url)، [ClamD protocol](https://docs.clamav.net/manual/Usage/ClamdProtocol.html)، [ClamAV Docker](https://docs.clamav.net/manual/Installing/Docker.html)، [AWS SDK S3](https://docs.aws.amazon.com/AmazonS3/latest/developerguide/s3_example_s3_PutObject_section.html). اختبارات S3 وMeta تستخدم fakes ولا تثبت Provider live.

## سلامة البيانات والصلاحيات

### المرفقات الصادرة ومرحلة Meta asset upload

Migration `033` توسع المرفق إلى origin محكوم: إما inbound Integration Event أو upload جاهز مرتبط بـConversation وبالمستخدم ومفتاح idempotency. Upload API يتحقق من Session/Lead scope قبل body parsing، ويحد كل replica بطلبين متزامنين وbodyLimit تقني قابل للإعداد. يفحص MIME من bytes والبصمة ثم ClamAV؛ لا يحفظ bytes أو metadata جاهزة قبل نجاح الفحص. اختير scan متزامن bounded للرفع التفاعلي لأن الحجم وعدد الطلبات محدودان، بينما بقي تنزيل inbound والإرسال الخارجي في workers مستقلة. فشل الفحص يعيد خطأ ظاهرًا بلا مرفق قابل للاستعمال؛ يعيد فحص Lead access داخل المعاملة بعد I/O. عند replay يستعمل معرّف الملف نفسه، ويزيل object جديدة غير مرتبطة عند تعارض معروف أو رفض Business بعد الفحص. عند نتيجة DB commit مجهولة يحتفظ بالملف الخاص بدل حذف object قد تكون مرتبطة فعلاً؛ تنظيف objects غير المرتبطة بعد هذه الحالة يحتاج reconciliation/retention محافظ، ولم يُختبر restore أو garbage collection بعد.

دعم outbound الحالي `JPEG/PNG/PDF` و`OGG/Opus, MP3, M4A/AAC` و`MP4/H.264` مع AAC واحد أو بلا audio، وWebP sticker ثابتة أو متحركة. Sender capabilities وConversation API تعرضان الأنواع وMIME والحد الأدنى بين حد infrastructure وحد adapter مع caption support؛ الواجهة لا تختار نوعاً بناء على MIME وحدها. لا تُقبل attachment تخص inbound أو Conversation أخرى، ولا ملف غير READY، ولا استعمال المرفق نفسه في Message أخرى؛ تبقى retry الخاصة بالنية نفسها على Message التاريخية. Central Messaging Policy تفحص Controller/Consent/DNC/Pinned Sender/Scope/Window/Capabilities عند enqueue وعند dispatch. Caption حتى 1024 لـimage/document/video فقط؛ audio/sticker ترفض النص بدلاً من إسقاطه، بما في ذلك DB trigger `038` وrecovery. media freeform خارج نافذة Meta تحتاج قالباً، ولا تُرسل في هذا المسار. Media template headers مدعومة بمسار مستقل موضح أدناه.

Profile `meta-cloud-media-2026-10-04` مستقل داخل adapter: image ≤5 MiB وaudio/video ≤16 MiB وdocument ≤100 MiB، مع سقف infrastructure الافتراضي25 MiB؛ WebP 512×512 بحد100 KiB للثابتة و500 KiB للمتحركة. هذه حدود protocol قابلة لتحديث adapter بعد مراجعة وثائق المزود، ولا تستخدم كقواعد Business أو كحد throughput. [Meta media reference](https://www.postman.com/meta/whatsapp-business-platform/folder/13382743-ecb27be5-4d27-4763-bbee-6a8002c04bf3) و[WhatsApp sticker reference](https://github.com/WhatsApp/WhatsApp-Nodejs-SDK/blob/main/website/docs/api-reference/messages/sticker.md) توثقان الأنواع/الحجم وstatic/animated. RIFF metadata parser bounded وفق [WebP specification](https://developers.google.com/speed/webp/docs/riff_container) يفحص chunks وcanvas/animation/dimensions دون decoding أو execution.

بعد bytes/hash validation وClamAV، يفحص ffprobe streams للصوت والفيديو عبر stdin فقط، مع `shell=false` ونافذة مخفية وprotocol whitelist `pipe` وformat whitelist `mov,mp3,ogg`؛ لا تصل filenames أو URLs خارجية أو filesystem paths من المستخدم إلى العملية. stdout/stderr bounded64 KiB وtimeout10s وstream count bounded؛ diagnostics لا تعاد ولا تسجل. [ffprobe](https://ffmpeg.org/ffprobe.html) dependency infrastructure في API وoutbound worker/CI، تضبط `MEDIA_PROBE_BINARY` من installation موثوقة. عند غيابها يفشل upload بـ503 آمن قبل READY، والعامل retry bounded دون provider I/O. metadata validation لا تدّعي فك/تصحيح كل frame أو قبول Meta حي؛ المزود قد يرفض media وتبقى قواعد failure/recovery الحالية. Worker يعيد فحص bytes/profile قبل رفعها، ثم يعيد السياسة قبل dispatch. file-type aliases لـOpus/M4A تطبع من detection فقط، دون الثقة بـMIME العميل.

Meta adapter يفصل `uploadMedia` عن `sendMedia`: upload قد يُعاد عند timeout/5xx لأنه يرفع asset ولا يرسل للعميل. Worker يقرأ bytes الخاصة ويعيد type/size/hash validation، ويفحص السياسة قبل الرفع ثم بعدها مباشرة قبل تسجيل `PREPARED` وcustomer send. تغير DNC أو Controller/Authorization أثناء asset upload يمنع customer dispatch؛ انتهاء lease قبل PREPARED قابل للاسترداد، وبعده يصبح UNKNOWN وفق القاعدة القائمة. Lease للرسائل media 180 ثانية لتغطية I/O bounded، بينما Text/Template يبقيان 60 ثانية. 429 يعمل ضمن backpressure الحالية، وأي customer send مجهولة النتيجة لا يعاد تلقائياً. Delivery callbacks تستعمل سجل Message نفسه ولا تعدّل محتوى المرفق. [مواصفات Meta media](https://www.postman.com/meta/whatsapp-business-platform/folder/13382743-ecb27be5-4d27-4763-bbee-6a8002c04bf3) و[تدفق رفع media لدى WhatsApp](https://whatsappbusiness.com/blog/media-messages-via-app/) مراجع adapter فقط؛ limits المزود لا تصبح ثوابت Business في Core.

S3 configured adapter يتطلب credentials deployment صريحة بأسماء `MEDIA_S3_ACCESS_KEY_ID` و`MEDIA_S3_SECRET_ACCESS_KEY` وsession token اختيارية؛ لا يستدعي credential discovery ولا profile شخصية من `~/.aws`. لا توضع هذه القيم في Git أو Business UI لأنها infrastructure credentials للتخزين، وليست Messaging provider credentials. Factory adapter يقبل S3 client آخر يحقن runtime credentials عند تكامل workload identity صريح؛ configured runtime الحالي يستخدم القيم المذكورة فقط.

- ثلاثة Roles فقط: `SUPER_ADMIN`, `MANAGER`, `AGENT`. Manager محصور بفرعه، وAgent بالـLeads المسندة له. Conversation وMessage وAI summary تتبع Lead access. الحقول تُفحص عند القراءة والكتابة والتصفية والتصدير.
- `Contact` منفصل عن `Lead`؛ Source Submission غير قابلة للاستبدال بقيم Lead التشغيلية. الحالات `OPEN/CLOSED/ARCHIVED` منفصلة عن Campaign Status. `Payment` منفصل عن `Enrollment`.
- في Manual intake تُحفظ قيم Contact الأصلية داخل `source_submission`، بينما تستخدم المطابقة هاتف E.164 بعد إزالة فواصل العرض وبريداً مطبّعاً بـNFKC والحروف الصغيرة. القيمة غير الصالحة تُرفض حتى لو وُجد معرّف آخر صالح؛ لا يُخمن Country code. تُؤخذ أقفال PostgreSQL advisory بترتيب ثابت لكل هوية قبل المطابقة والإنشاء، فلا تنشئ الطلبات المتزامنة Contact مكرراً لنفس الهوية في هذا المسار. وجود Contact سابق لا يدمج Leads.
- عند تطابق أكثر من Contact، أو تطابق Contact موجود خارج فرع Manager دون Lead سابقة في فرعه، تُحفظ Source Submission في `NEEDS_ATTENTION` ولا تنشأ Lead. صفحة المراجعة تعرض مرشحي الفرع فقط؛ إذا تضمّن القرار أي مرشح خارج الفرع أو Contact مشتركة بين فروع، يحسمه Super Admin. تُقفل Submission عند الحسم ويصبح تكرار الطلب بالقرار نفسه آمناً، بينما يُرفض قرار مختلف. تعديل الهوية يستخدم `version` لمنع الكتابة المتزامنة المفقودة، ويحفظ `contact_history` و`audit_log`، ولا يسمح لManager بتعديل Contact مشتركة بين فروع. فهارس البحث والقوائم وkeyset pagination تحصر البيانات في Leads المصرح بها.
- `Field Definition` لها نطاق Global/Branch/Campaign و`value_mode` يميّز Manual/Source/System/Calculated؛ لا يسمح مسار المستخدم بكتابة Source/System/Calculated. الربط بالحملة يحمل ترتيب العرض، صلاحيات Agent/Manager، مواضع العرض، والفترة التي تُطلب فيها القيمة (`LEAD_CREATION` أو `CLOSE` أو `ENROLLMENT`). الكتابة تمر بتحقق النوع والخيارات والحدود في Backend، و`version` يمنع فقد تعديل التعريف/الربط/القيمة المتزامن. `field_value_history` يحفظ التغييرات ولا يمحو Raw Source Submission. الحقول المحسوبة تستخدم سجل وظائف مشتقة محدد مسبقاً من Queries موثوقة؛ لا تُقبل صيغ حرة من المستخدم أو ناتج AI كحقيقة تشغيلية، ولا تدخل محاولات AI في عداد Human Agent. تحقق `ENROLLMENT` يُربط بخدمة Enrollment عند بنائها. بحث Leads بحقل مخصص يتحقق من `filterable` وVisibility ونوع القيمة في Backend، بينما Export ينتظر مساره.
- إعداد Campaign يستخدم `version` لمنع ضياع تعديلين متزامنين، ويمنع تعديل خصائص التشغيل وهي `ACTIVE` حتى تُعطّل صراحة. التفعيل والتعطيل وتغييرات Agent تُقفل صف Campaign داخل معاملة وتُدقّق؛ Manual intake يقفل Branch ثم Campaign ويعيد فحص الحالة داخل المعاملة، حتى لا تنشأ Lead بعد سبق تعطيل الحملة. تعرض Readiness أسباباً قابلة للفهم؛ يبقى Source الخارجي وMessaging وAI وPerformance routing محجوباً عن Activation إلى أن تعمل خدماتها والتحققات الفعلية. تعريف Conversion الاختياري لا يُستنتج من إغلاق Lead؛ حالياً يُقبل Milestone مؤكد للدفع أو التسجيل كإعداد فقط، ولا يُعرض Conversion rate قبل بناء Analytics المرتبطة.
- إعادة إسناد Lead داخل الفرع تقفل صف Lead وتفحص `version` ودور المستدعي وفرع Agent المستهدف. تُحفظ `assignment_history` و`lead_activity` و`audit_log` داخل المعاملة نفسها، وتنتقل المهام المفتوحة المملوكة للـAgent السابق وHuman conversation controller معه مع حفظ تاريخ كل انتقال. لا يحدث نقل فرع ضمن هذا المسار، إذ يتطلب معالجة Campaign وSender وConversation منفصلة. الملاحظات الداخلية تسجل في النشاط ولا تدخل مسار الرسائل الخارجية. متابعة Human لها `version` وتاريخ append-only؛ إكمالها/إلغاؤها لا يحذف السجل.
- البحث يطبق نطاق Lead في SQL قبل الفلاتر وkeyset pagination؛ حقل Campaign غير المرئي أو غير القابل للتصفية يُرفض قبل الاستعلام. Sorting لتاريخ الإنشاء صعوداً/هبوطاً يستخدم `(created_at, id)` كمفتاح ثابت ويطابق اتجاه المؤشر مع `ORDER BY`؛ قيمة الاتجاه الخام لا تأتي من المستخدم بل من enum موثوق. Saved View تحتفظ بالفلتر والأعمدة الاسمية والمالك والنطاق والنسخة، ولا تحمل صلاحية مستقلة؛ عند تطبيقها يعيد مسار Leads فحص صلاحيات المستخدم الحالية. اختيار الأعمدة في الواجهة محصور بحقول Lead التشغيلية المصرح بها، والـAPI يتحقق من القائمة عند الحفظ. إنشاء/تعديل المشهد يتحقق من النطاق والحقل ويستخدم `version` وتعارض الاسم. Bulk assignment المتزامن محدود بـ50 Lead ويتطلب تأكيدًا؛ يستدعي خدمة الإسناد الفردي نفسها في معاملة مستقلة لكل Lead، ويعيد نتيجة كل عنصر. تمنع نسخة Lead تكرار الأثر عند retry أو طلبين متزامنين. العمليات الكبيرة ذات Progress دائم، وبقية إجراءات Bulk ومفاتيح ترتيب إضافية، لا تزال غير مكتملة.
- قيود unique على provider event ID وmessage idempotency key وpayment reference، وتاريخ assignment/field/handoff/payment/knowledge/audit append-only. تتحقق المعاملات من الحالة الحالية قبل transition. callbacks القديمة لا تُرجع الحالة إلى الوراء.
- تسجيل دخول بلا Public Signup. Bootstrap لأول Super Admin يحتاج secret عشوائياً في بيئة النشر ويُقفل transactionally عند النجاح؛ يقارن الرمز بآلية ثابتة الزمن ولا يُحفظ في قاعدة البيانات. Reset tokens أحادية الاستعمال ومحدودة المدة. تعطيل المستخدم يبطل جلساته. Cookies `HttpOnly`, `Secure` في الإنتاج، `SameSite=Lax`، والتحقق من Origin/CSRF للطلبات المغيّرة.
- إنشاء المستخدم بعد التهيئة يتم بالدعوة: لا يحدد المسؤول كلمة مرور الموظف. `credential_token` يحتفظ بـSHA-256 للرمز فقط، وتُشفّر نسخة التسليم في job بـAES-GCM وAAD خاص بالـjob؛ رابط البريد يضع الرمز في URL fragment فلا يُرسل إلى خادم الواجهة ضمن HTTP request. Reset/Invitation تستهلك الرمز atomically وتُبطل الرموز القديمة، وReset يبطل جلسات المستخدم. Email adapter يفصل SMTP عن منطق الحسابات، وConnection المشفرة تضبط من داخل المنصة. Worker مستقل يستخدم PostgreSQL leases و`SKIP LOCKED` وretries bounded؛ لوحة الإدارة تعرض حالات التسليم دون payload أو secrets. لا يُعد اختبار fake تحققاً مباشراً من SMTP.
- credentials مشفرة في قاعدة البيانات، ومفتاح التشفير deployment secret خارج قاعدة البيانات. API لا يعيد قيمتها، ولا تدخل logs أو AI context.

## الرسائل والـAI

مرحلة إعداد Messaging الحالية تُخزن `IntegrationConnection` بنطاق Organization أو Branch ونسخة تحديث متفائلة، وتُشفّر مجموعة credential باستخدام AAD المرتبط بالاتصال. `MessagingProviderAdapter` يفصل اكتشاف Senders عن قاعدة البيانات؛ Adapter الخاص بـMeta يجلب Phone Numbers من Graph API بمسار/حقول ثابتة وصفحات محدودة ومهلة اتصال، ولا يتبع `paging.next` القادم من المزود كعنوان URL. اختبار الاكتشاف لا يثبت الإرسال، لذلك يعيد `WARNING/SEND_NOT_TESTED` وSender health `UNKNOWN`. يعرض Manager اتصال Organization وأرقامه المربوطة بفرعه فقط، ويبقى تعديل هذا الاتصال لدى Super Admin. إعادة التهيئة تتطلب فحصًا جديدًا؛ ويظل Sender غير المكتشف غير نشط. هذا checkpoint لا يربط بعد قواعد الإرسال بخدمة API أو Worker.

يُفصل `messaging_sender.active` الذي يعكس وجود الرقم في آخر اكتشاف عن `operator_enabled` الذي يعكس قرار الإدارة؛ لا يعيد اكتشاف الرقم تشغيل Sender عطّلته الإدارة. يتطلب ربط Sender واسع النطاق بفروع بعينها حدثًا صريحًا من Super Admin، وخيار `allow_shared_fallback` منفصل عن مجرد السماح باستخدامه. تخزن `branch.default_sender_id` و`campaign.sender_override_id` اختيارات إعداد قابلة للإبطال؛ تغييرها يستخدم version، ويمنع Backend اختيار رقم خارج نطاق الفرع أو غير متاح. يبقى `WARNING/UNKNOWN` حاجزًا للإرسال حتى عندما يمكن حفظ الإعداد. لا يُفك Binding مستخدمة في Default/Override بصمت؛ إبطال Sender لاحقًا يجب أن يحظر المحادثة المثبتة بدل تغيير هويتها تلقائيًا. تثبيت Sender في Conversation هو الخطوة التالية.

خدمة `resolveConfiguredSender` تقرأ Campaign/Branch في نطاق Organization ثم تجلب Sender المعدّ فقط، أو بحد أقصى مرشحين اثنين للـShared fallback؛ هذا يكفي لاكتشاف الالتباس بلا تحميل كل Senders. تعيد استعمال `resolveSender` نفسها، وتتحقق من `active` و`operator_enabled` و`CONNECTED` وhealth وtext capability. Pinned Sender يدخل بأولوية مطلقة ولا يعود إلى Override/Default إذا بطل؛ تُعاد `PINNED_*` كسبب صريح. API المعاينة للإدارة لا تنشئ Conversation أو ترسل شيئًا.

فتح Conversation يتم بقفل صف Lead ومعرفة رقم Contact المطبع، وفحص Scope المستخدم داخل استعلام القفل. قيد جزئي يمنع محادثتين نشطتين للقناة نفسها على Lead واحدة، والطلب المكرر يعيد القائمة دون تغيير Controller. تُربط Conversation بالـSender وConnection الناتجين من الحسم؛ لاحقاً تُعاد قراءة هذا الـSender بصفته Pinned في كل تفاعل. عند تعطيله أو خروج نطاقه أو تغير Participant Reference أو اختلاف Connection المخزّن عن Sender يُحفظ `needs_attention_reason` ويُمنع فتح بديل تلقائي. مسارات القراءة تربط Conversation بـLead access داخل SQL. فتح المحادثة لا يرسل رسالة ولا يتجاوز Central Messaging Policy المطلوبة للرسائل اللاحقة. يُضاف قيد DB مركب يحرس تطابق Sender/Connection عند مرحلة Message integrity التالية.

حالة WhatsApp Consent تحفظ على Contact/Channel كي تؤثر في جميع Leads المربوطة بالهوية نفسها؛ `do_not_contact` قرار منع مستقل عن opt-in. غياب الصف يعني `UNKNOWN` ولا يساوي موافقة. تحديثها يقفل Lead ثم Contact ويستخدم version لمنع lost updates، ويسجل snapshot في history وحدث Audit دون نسخ evidence إلى Audit. Manager لا يغير Consent إذا كان Contact مرتبطًا بفرع آخر، وAgent يقرأ حالة Lead المصرح بها فقط. Central send service التالية تقرأ هذه الحالة داخل سياق Lead وتحظر `REVOKED` أو DNC، وتطبق سياسة متطلبات الموافقة للقناة والحملة قبل أي outbound.

تخزن نافذة Branch المحلية في `messaging_window` مع `messaging_policy_version` مستقل عن نسخة Sender، وتعرض Campaign نافذتها الاختيارية في `messaging_policy` مع `maxAttempts` و`minIntervalSeconds`. `null` في Campaign يرث نافذة Branch؛ `null` في Branch يعني غياب قيد زمني محلي، ولا يلغي قواعد المزود أو الموافقة. نافذة تعبر منتصف الليل مقبولة، وتحسب خدمة الإرسال الزمن وفق IANA timezone للفرع. إعداد Campaign يستخدم `campaign.version` الموجود؛ كل كتابة تقفل الصف وتدقق، لكن إعداد السياسة ليس دليلاً على جاهزية الإرسال. الأرقام الموجبة محددة بحد integer تقني، دون فرض حد تجاري افتراضي. تُحدد دلالة عدّ المحاولات وأنواع الرسائل الخاضعة لها في خدمة الإرسال المشتركة قبل تفعيلها؛ لا يقرأها مسار إرسال جزئي أو يتجاوزها.

يُفصل `IntegrationConnection` عن `MessagingSender`. للإرسال الجديد: Campaign override ثم Branch default ثم Organization shared fallback المسموح. المحادثة القائمة تُثبت sender/thread؛ عند عدم صلاحيته تُحظر الرسالة وتظهر Needs Attention. كل Human/AI/Automation/Follow-up send يدخل خدمة واحدة تفحص الصلاحية، controller، consent/DNC، template، نافذة الوقت والمنطقة الزمنية، الصحة والنطاق، حدود الحملة وقدرات المزود. تُحفظ `QUEUED` داخل معاملة قبل اتصال المزود، ويستهلكها worker مع retries محدودة ومفتاح idempotency. inbound webhook يُتحقق منه ويُحفظ كـIntegration Event قبل حل هوية المحادثة؛ الغموض يذهب لمراجعة بشرية.

مسار Human outbound الحالي يستدعي `enqueueOutboundMessage` بعد المصادقة؛ هذه الخدمة هي مدخل القرار المركزي ولن يُفتح مسار AI أو Automation مستقل يتجاوزها. ترتيب القفل Lead ثم Contact ثم Conversation يمنع إرسالين متزامنين من تجاوز حالة الاتصال أو تكرار المفتاح، وينسق مع تغيير Consent/إسناد Lead. يُعاد الطلب بالمفتاح نفسه والبيانات نفسها إلى Message الأصلية، ويُرفض تغيير المحتوى تحت المفتاح. تحفظ رسالة `QUEUED` ومهمة `background_job` ورابطهما وAudit داخل معاملة واحدة. يمنع FK مركب اختلاف Connection/Sender عن Conversation، ويمنع trigger تعديل هوية/محتوى الرسائل أو حذفها مع السماح بتقدم حقول التسليم. GET الرسائل يعيد فحص صلاحية Lead في SQL، وتعرضها React كنص غير موثوق بلا HTML. حد Campaign للمحاولات والفاصل يخص المحاولات الاستباقية `AI/AUTOMATION/FOLLOW_UP`؛ الرد البشري يمر ببقية السياسة ولا يستهلك هذا الحد. هذا التفسير مستند إلى تسمية `Follow-up Frequency / Max Attempts` في وثيقة 05، ويحتاج اختبارات تشغيلية عند بناء تلك المصادر.

بالنسبة إلى Meta WhatsApp Cloud، يرفض مسار النص الحر عند غياب Inbound موثوق ضمن نافذة خدمة العميل البالغة 24 ساعة؛ السياسة الحالية موثقة في [WhatsApp Business Messaging Policy](https://whatsappbusiness.com/policy/). لا يعني هذا السماح بإرسال Template غير معتمدة؛ مسار القوالب والتحقق من حالتها سيبنى منفصلاً. يجب أن يعيد worker تقييم كل قيود الإرسال قبل Provider call، لأن Consent أو Controller أو Sender أو النافذة قد تتغير بعد حفظ `QUEUED`. الاتصال المُكتشف وحده يبقى `WARNING/SEND_NOT_TESTED` ولا يتحول إلى `CONNECTED` اصطناعياً في الإنتاج.

عامل Messaging الحالي يستخدم `background_job` و`SKIP LOCKED` مع `sender_outbound_lease` ليمنع توازي طلبين من Sender نفسه، و`outbound_send_attempt` بحالة `PREPARED` تُحفظ قبل الاتصال الخارجي. يعيد العامل استعمال `checkCurrentOutbound` بعد قراءة هوية Human الحالية، ثم يفك credential داخل العملية فقط. Meta adapter يرسل Text إلى `/{phone-number-id}/messages` وفق [مجموعة Meta الرسمية](https://www.postman.com/meta/whatsapp-business-platform/folder/o48mro7/messages)، بمهلة 10 ثوانٍ وبدون كشف تفاصيل مزوّد أو Token في الأخطاء. استجابة مزوّد موثقة بـMessage ID تحفظ `SENT`؛ `429` المؤكد يعاد بمهلة وحد محاولات، بينما timeout/5xx/استجابة ملتبسة أو انقطاع Job بعد بدء المحاولة ينتهي بحالة `UNKNOWN` وNeeds Attention دون Retry تلقائي. هذا قرار احترازي لأن عقد الإرسال الذي تحققنا منه لا يثبت مفتاح idempotency من العميل؛ إعادة المحاولة العمياء قد ترسل رسالتين. تُعرض `UNKNOWN` بوضوح في الواجهة، وتُحفظ نتائج worker في Audit دون نص الرسالة أو الأسرار. لا تُعد هذه اختبارات Live Provider؛ اختبارات worker الحالية تستخدم حالة `CONNECTED` مصطنعة، بينما اختبارات test-send مستقلة تستخدم fake adapter.

Catalog قوالب Meta يستخدم adapter منفصلاً لطلبات WABA `/{WABA-ID}/message_templates` وفق [مرجع Meta الرسمي](https://www.postman.com/meta/whatsapp-business-platform/folder/lczy75a/templates). تعدد الصفحات محدود تقنياً إلى 100 صفحة/10,000 قالب؛ تجاوز الحد يفشل بوضوح دون إيقاف قوالب محفوظة. المزامنة الكاملة فقط توقف القوالب الغائبة وتحدث Approval/status وComponents داخل معاملة، مع فحص نسخة Connection بعد نداء المزود، وتحفظ زمن اكتمالها كي لا تستخدم مراجعة قديمة. الإنشاء المتاح تشغيلياً حالياً لقالب `MARKETING/UTILITY` بنص BODY ثابت أو ذي متغيرات نصية وأمثلة اعتماد مع HEADER TEXT ثابت أو ذي متغير واحد وFOOTER اختياريين؛ يسجل الطلب ومفتاح idempotency قبل النداء الخارجي، ويمنع تكرار الطلب إذا تعذر الجزم بنتيجته. مزامنة القالب قد تحسم طلباً ملتبساً عند ظهور اسم/لغة القالب في WABA. إذا بقي الطلب مجهول النتيجة أو انقطعت العملية `IN_PROGRESS` لأكثر من دقيقتين، تسمح واجهة المراجعة للمسؤول بتأكيد غياب القالب فقط بعد مزامنة كاملة أحدث من الطلب وبنسخة الاتصال نفسها؛ يسجل القرار في Audit، ويصبح مفتاح جديد مسموحاً مع التنبيه لاحتمال تأخر ظهور القالب لدى المزود. لا يحدث retry تلقائي لطلب خارجي ملتبس. تعديل Connection أو تعطيلها يبطل صلاحية Catalog المحلية إلى حين مزامنة صحيحة. صلاحية Catalog لاتصال Organization تخص Super Admin، وManager لاتصال فرعه؛ مجرد Binding لرقم مشترك لا يكشف قوالب اتصال المؤسسة. نجاح إدارة Catalog لا يغيّر Connection إلى `CONNECTED` ولا يثبت test-send.

لإرسال Template، تحفظ `campaign_message_template_binding` سماحاً صريحاً لكل Campaign/Template مع version وAudit. Manager لاتصال Branch يرى ويضبط قوالب فرعه؛ في Organization shared connection يضبط Super Admin الربط، بينما يرى Manager القوالب المرتبطة بحملته فقط. Agent يرى من Conversation المصرح بها القوالب النصية المركبة المدعومة `APPROVED` المربوطة بحملتها فقط. الرسالة تحفظ `message_kind` و`template_id` وSnapshot من الاسم واللغة وComponents والنص، ويمنع trigger تعديلها. `enqueueOutboundMessage` يطبق السياسة المركزية ويثبت BODY النصي وقيمه المختارة من القالب بدلاً من نص Template حر يقدمه المستدعي؛ يعيد Worker فحص صلاحية القالب وربطه واعتماده وتطابق Snapshot قبل `/{phone-number-id}/messages` مع `type=template`، وفق [مرجع Meta لإرسال القوالب](https://www.postman.com/meta/whatsapp-business-platform/request/lwtlz1k/send-message-template-interactive). تغير القالب أو سحب اعتماده يمنع الإرسال ويظهر Needs Attention، ولا ينتقل تلقائياً إلى قالب آخر. دعم BODY text variables موضح لاحقاً؛ HEADER TEXT ثابت/متغير واحد وFOOTER مدعومان؛ CTA ثابتة وURL suffix مدعومة؛ Quick Reply مدعومة كما أدناه؛ Media template headers مدعومة كما أدناه، ولا تثبت هذه الاختبارات Live Provider.

اختبار إرسال الاتصال مسار إعداد تشغيلي مستقل عن رسائل العملاء المرتبطة بـLead. لا يسمح به إلا لمسؤول اتصال Organization أو Manager اتصال فرعه، بعد تأكيد سيطرته على رقم الاختبار أو موافقته، ويقتصر على Sender مكتشف نشط وقالب `APPROVED` ثابت. يحفظ `messaging_connection_test_send` نية الاختبار قبل نداء Meta مع HMAC لمحتوى الطلب ومفتاح idempotency؛ يحتفظ بآخر أربعة أرقام من المستلم فقط. يعيد المفتاح الناجح النتيجة دون نداء جديد، ويمنع المفتاح الملتبس أو المتقادم الإرسال التلقائي حتى تُراجع Meta. قبول Provider Message ID يجعل Connection الحالية `CONNECTED` بقدرة `outboundAccepted` و`webhookVerified=false`، وSender المختبر `DEGRADED` إلى حين تحقق التسليم والـWebhook. لا يُفعّل اتصال تغيرت نسخته أثناء النداء. `401/403` من المزود يبطل المصادقة (`AUTH_EXPIRED`) ولا يسمح بالإرسال حتى إعادة إعداد الاتصال. لا يحل هذا المسار محل Central Messaging Policy لأي رسالة Lead؛ نتيجة قبول المزود لا تعني `DELIVERED` أو نجاح Webhook. الاختبارات تستخدم fake provider، لذلك تبقى Live verification معلقة على اعتماد خارجي مخصص.

Meta Messaging Webhook يستخدم عنواناً مستقلاً لكل Connection، والتحقق GET من Verify Token المحفوظ مشفراً، والتحقق POST من `X-Hub-Signature-256` بـHMAC-SHA256 على الـRaw Body قبل JSON parse. يفحص WABA ID ونوع `messages` وSender ID والحجم وعدد العناصر، ولا يسجل payload أو Credential في الخطأ. يربط كل Status بمفتاح حدث SHA-256 مشتق من Sender وProvider Message ID والحالة ووقت المزود والمستلم؛ قيد `integration_event(connection_id, provider_event_id)` يمنع replay/duplicate. `message_delivery_event` يحتفظ بكل Status صالح حتى لو لم يغير الحالة الحالية. تحديث الحالة محكوم بزمن المزود وترتيب `SENT < FAILED < DELIVERED < READ`؛ لا يعيد `sent` أو `failed` متأخراً رسالة مقروءة إلى الوراء. يتحقق من Connection وSender وParticipant قبل تعديل Message، ويضع اختلاف الهوية في `NEEDS_ATTENTION`. إذا سبق callback كتابة Provider ID، يحفظ الحدث `MESSAGE_NOT_FOUND` ويعيد Worker تسويته بعد ظهور ID، دون تخمين Message من التوقيت أو الهاتف. `DELIVERED/READ` الموقّعة تجعل صحة Sender `HEALTHY`، بينما GET handshake أو قبول outbound وحدهما لا يثبتان التسليم. حدث inbound موقّع يُحفظ بالمعرف والـpayload المحدود في `NEEDS_ATTENTION` قبل أن يعالجه Worker؛ النص ذي المطابقة الوحيدة يلحقه بمحادثة، والغموض والوسائط يبقيان للمراجعة دون رد تلقائي. تعديل/تعطيل Connection يمحو أعلام التحقق من نسختها الجديدة، وطلب callback الذي يستخدم نسخة قديمة لا يفعّل النسخة الجديدة. المراجع: [Meta Message Status Notifications](https://www.postman.com/meta/whatsapp-business-platform/request/rgtfq23/message-status-update-notifications)، و[Meta Webhook setup](https://developers.facebook.com/docs/graph-api/webhooks/getting-started/).

خدمة inbound text تستهلك `integration_event` المحفوظة في Worker على دفعات محدودة. تبدأ بـConnection/Sender والـparticipant المطبع؛ إذا حملت رسالة Meta `context.id` تفحص Provider Message ID السابقة وتطابق participant، ثم تبحث Conversation نشطة بالنطاق نفسه، ثم Contact/Lead مفتوحة فقط إذا كان Sender يطابق Campaign override أو Branch default أو fallback مشتركاً مصرحاً به. تحفظ Message برقم المزود تحت قيد فريد، وتُقفل صف Lead قبل إنشاء Conversation حتى لا ينشئ حدثان متزامنان محادثتين. لا تعيد فتح مغلقة ولا تبدل Sender مثبتاً ولا تختار بين Leads متعددة. الرسالة غير النصية أو الغامضة تبقى حدثاً `NEEDS_ATTENTION` مع سبب. Review API لا يعرض Candidate Leads خارج فرع Manager؛ اتصال Organization المشترك تراجعه Super Admin فقط. الحسم الصريح أو التجاهل يقفل الحدث ويحفظ Audit وسبب التجاهل دون حذف payload، ومحتوى العميل يعرض كنص غير موثوق في React. Conversation الجديدة بلا Agent نشط تبدأ `WAITING_FOR_HUMAN`; takeover يغير Controller إلى HUMAN بنسخة متفائلة ويحفظ `conversation_handoff`. عند وصول inbound إلى AI Controller تُمنع الإجابة الآلية وتصبح `AI_HANDOFF_REQUIRED` إلى أن تُنفذ دورة AI/handoff الكاملة. media/attachments المدعومة تعالج وفق القسم الخاص بها؛ حسم Campaign من مرجع إعلان خارجي غير منفذ بعد، ولا يثبت الاختبار تشغيل Webhook حياً.

الـAI يستقبل Effective Configuration حتمية: Global guardrails الثابتة، Branch defaults المسموحة، Campaign config ونسخة Published Knowledge. كل execution مربوط بـCampaign/Lead/Conversation/knowledge version. لا يحصل النموذج على SQL أو credential. الأدوات المسموحة تستدعي application services ذات الصلاحيات ذاتها. الأسئلة التجارية بلا سند تُصعّد؛ الدفع لا تؤكده رسالة عميل أو قرار نموذج. عند `HUMAN_ACTIVE` لا يحدث AI auto-send.

عند `429` صريح من مزود الإرسال يثبت Worker `cooldown_until` على Connection وSender في PostgreSQL، وليس على Job المفردة فقط. استعلام claim يستبعد Jobs المعلقة لاتصال غير `CONNECTED` أو Sender غير جاهز أو فترة انتظار لم تنتهِ؛ تظل الرسائل تاريخياً `QUEUED` إلى أن تعود الجاهزية ويعاد فحص Central Messaging Policy. يعيد `prepare` فحص الجاهزية قبل تسجيل `PREPARED`، وإن تغيّرت بعد claim يعيد Job إلى الطابور دون إنفاق محاولة أو Provider call. محاولة `RUNNING` انتهى lease الخاص بها بعد تسجيل `PREPARED` تُحسم `UNKNOWN` حتى لو تعطل الاتصال، لأن تكرارها قد يرسل نسختين. رد `401/403` يجعل Connection `AUTH_EXPIRED` وكل Senders التابعة لها `UNKNOWN`. test-send التشغيلي يحترم cooldown نفسه ويخزن رفض `429` مؤكداً مع idempotency. Queue-health API يحسب العمق فقط من Jobs النشطة، ويحصر Manager بفرعه حتى على Connection مشتركة. هذه آلية backpressure تفاعلية مبنية على إشارة المزود؛ حدود Meta المتغيرة ليست Business constants، ولا تثبت جودة throughput أو اختبار حمل أو تكامل حي.

لقوالب Meta ذات `BODY` نصي متغير، يفحص الخادم تسلسل placeholders وعددها قبل إنشاء طلب القالب ويطلب أمثلة اعتماد Meta، ثم يحفظ Catalog المعتمد كما عاد من المزود. عند إرسال Human يثبت `template_snapshot` النص الأصلي والقيم المختارة والنص النهائي في Message غير قابلة للتعديل؛ لا تُشتق القيم من Lead أو AI تلقائياً. يعيد Worker فحص النسخة والاعتماد والربط والقيم، ويرسل `components: [{ type: 'body', parameters: [{ type: 'text', text }] }]` عبر Meta adapter. اختلاف القيم مع مفتاح idempotency نفسه مرفوض. قوالب BODY الثابتة السابقة تبقى Snapshot متوافقة. حصر parser بـ10 متغيرات حد تقني محافظ للمدخلات، وليس ادعاءً عن حد مزود متغير؛ Header/Buttons/Media تحتاج مسارات capabilities واختبارات مستقلة. مرجع شكل Create/Send: [Meta template example](https://www.postman.com/meta/whatsapp-business-platform/request/ep5w4rc/create-template-w-document-header-text-body-a-phone-number-button-and-a-url-button)، [Meta template send](https://www.postman.com/meta/whatsapp-business-platform/request/lwtlz1k/send-message-template-interactive).

`needs_attention_reason` ليس علامة عرض مؤقتة: إعادة فتح Conversation لا تزيل إلا مشكلة Sender/participant المثبتة بعد زوالها، ولا تستبدل `SEND_OUTCOME_UNKNOWN` بمجرد انخفاض جاهزية Connection. لأسباب `SEND_OUTCOME_UNKNOWN` و`DELIVERY_FAILED` و`TEMPLATE_CHANGED` يوجد إقرار مراجعة versioned على مستوى Conversation، محصور بـSuper Admin أو Manager الفرع، مع ملاحظة إلزامية وAudit وتاريخ قابل للقراءة ضمن النطاق. الإقرار لا يغير Message التاريخية أو Delivery state ولا يعيد الإرسال؛ يزيل حاجز المراجعة فقط بعد قرار بشري ظاهر. إذا بقي Sender أو Consent أو Controller غير صالح، تمنع Central Messaging Policy أي إرسال جديد. استرداد Provider outcome آلياً عندما يكون مجهولاً يتطلب دليل مزود موثوقاً، فلا يوجد retry تلقائي قد يكرر رسالة العميل.

## التشغيل والنمو

### أقفال Messaging وقياس burst

#### Durable event ingestion وفصل workers

Webhook يحفظ حتى 100 حدث صالح في معاملة واحدة باستخدام bulk insert وlookup واحدة للـSenders؛ `200` يعني حفظ الحدث الدائم فقط. Status تبدأ `RECEIVED` ولا تغير Message داخل HTTP handler. `worker:events` تطبق callbacks وتسوية callback السابقة لـProvider ID وحل inbound بالتناوب، مستقلة عن `worker:messaging` الصادرة و`worker:media`، كي لا يعطل timeout إرسال أو تنزيل استقبال الرسائل وتسويتها. تغيير Delivery يظل محكوماً بالدليل الموقّع والـConnection/Sender/Participant وزمن المزود ورتبة الحالة، دون إرسال جديد أو تبديل Sender.

Migration `034` تحفظ عداد المحاولات والفشل وversion وموعد المحاولة وآخر معالجة وسجل attempts؛ `035` تحصن النهاية الخامسة ضد NULL/state غير FAILED، و`036` تفهرس global due queue بفلاتر صريحة مناسبة للاستعلام prepared. Worker تمسك Event بـ`SKIP LOCKED` ثم تنفذ Database mutations داخل savepoint؛ أي failure تلغي تغييرات Message/Attachment/Audit الجزئية قبل حفظ retry/history في المعاملة الخارجية. خمس failures متتالية مع backoff من 30 ثانية تقود إلى FAILED؛ crash قبل commit يلغي المعاملة كلها ويترك الحدث قابلاً لالتقاط عامل آخر. DB outage يمنع الحفظ مؤقتاً ويعيد cycle عند رجوعها، ولا يسجل نجاحاً أو يرسل للعميل. أسباب Needs Attention التجارية لا تتكرر بلا سبب، وMESSAGE_NOT_FOUND تعاد فقط عند ظهور Provider reference المطابقة.

واجهة Connection تميز pending/failed/review، تعرض آخر معالجة وأقدم حدث معلق، وتتيح filtering وhistory pagination دون payload أو أسرار أو هاتف كامل. إعادة FAILED فقط لمسؤول Connection ضمن النطاق، بملاحظة وversion وAudit، وتعيد عداد failures لا التاريخ أو الهوية. لا يمكن إعادة PROCESSED أو تجاوز review أو نتيجة send مجهولة بهذا API. المتغيران `MESSAGING_EVENT_BATCH_SIZE` (1–500، الافتراضي 50 لكل نوع في cycle) و`MESSAGING_EVENT_POLL_MS` (100–60000، الافتراضي 2000) إعدادات infrastructure bounded، لا provider limits؛ pool/concurrency عبر replicas تقاس قبل زيادتها. نجاح mock/worker smoke لا يثبت Meta live أو UI E2E.

حفظ Webhook يمسك Connection بـ`FOR NO KEY UPDATE` قبل إدخال الأحداث وتحديث آخر نجاح. استخدام `FOR SHARE` ثم ترقية القفل إلى UPDATE كشف deadlock `40P01` عند signed replay متزامن. نتائج outbound Worker وتسوية Delivery callbacks تمسك Connection قبل Job/Message/Sender للمحافظة على ترتيب mutations واحد؛ لا يوجد HTTP provider تحت القفل. `NO KEY UPDATE` لا يحجب FK key-share عند إدخال السجلات التابعة؛ [مرجع PostgreSQL](https://www.postgresql.org/docs/18/explicit-locking.html). تسلسل الحالة على Connection يحد burst على الاتصال الواحد، ولا يوقف Connections الأخرى.

Harness `benchmark:messaging` يستخدم HTTP loopback حقيقياً وpools مستقلة للنسخ والعمال ومزوداً وهمياً؛ لا يفتح اتصالاً إلا إلى `lead_operations_test` المحلية وبعد reset acknowledgement. يحفظ timings/counts دون credentials، ويثبت duplicate protection وper-Sender isolation وcooldown/recovery وcallback قبل ACK وout-of-order. القياسات والحدود في `messaging-performance.md`. callbacks أصبحت معالجة مستقلة بعد durable ingestion كما في القسم أعلاه؛ القياسات قبل الفصل وبعده موثقة، ولا تعني هذه النتائج اكتمال اختبار حمل إنتاجي أو Media/AI workloads.

جميع timestamps تخزن UTC؛ نافذة الإرسال والتقارير تُحسب بـIANA timezone للفرع أو override الحملة. القوائم تستخدم keyset pagination وفهارس على branch/campaign/owner/state/time. العمال يستخدمون leases و`SKIP LOCKED`، retries bounded وdead-letter قابل لإعادة المعالجة من واجهة إدارية مصرح بها. فصل queues حسب نوع العمل وأولوية الرسائل، مع حد تزامن لكل connection/sender. إدخال Webhook قصير ويحفظ الحدث قبل المعالجة. Logs منظمة بدون أسرار؛ health وqueue lag وconnection health وerror counters قابلة للرصد.

افتراضات السعة التقنية قابلة للقياس والتعديل: لا يحدد المنتج عدداً ثابتاً للـLeads أو senders؛ تضبط pool size وworker concurrency وbatch size من deployment config، وتُقاس p95 latency وqueue lag ومعدل retries قبل زيادتها. نسخ PostgreSQL احتياطياً مع اختبار استعادة دوري، وملفات object storage بنسخ/retention متوافق. migrations منفصلة وقابلة للتدرج في deploy قبل تفعيل الكود الذي يعتمد عليها.

## استرداد outbound قبل قبول المزود

Migration `037` تضيف `recovery_version` على رابط Message/Job وسجل `outbound_message_recovery` غير قابل للتعديل مع فهارس keyset لـdispatch attempts وDelivery events والاسترداد. API تفاصيل الرسالة تعرض Queue state وworker attempt count/budget/وقت الإتاحة وخطأ آمن، وثلاثة سجلات paginated دون Job payload أو raw provider response أو credentials/storage keys. صلاحية التاريخ هي Lead access الحالية؛ قفل مشاركة قصير على Lead يثبت الإسناد خلال القراءة، ولا يمنح التاريخ صلاحية مستقلة بعد reassignment. سجل dispatch يغطي `PREPARED/ACKNOWLEDGED/REJECTED/UNKNOWN` فقط؛ فشل policy أو media upload قبل customer dispatch يظهر في خطأ Job وعداده وقد لا يملك dispatch attempt.

الـrecovery ليست resend لأي Failed. تقبل فقط Message بشرية `FAILED` وJob `DEAD` بلا lease، ولا Provider ID أو sent timestamp أو delivery rank/event، وجميع dispatch attempts السابقة إن وجدت `REJECTED` مكتملة بلا Provider ID. `PREPARED/UNKNOWN/ACKNOWLEDGED` تمنعها، حتى إن تغيّرت Message أو Job state لاحقاً؛ فشل Delivery callback بعد ACK لا يصبح فشلاً قبل القبول. DB trigger يحمي العودة إلى QUEUED دون سجل recovery مطابق أو مع أي دليل قبول/غموض؛ Provider ID التاريخية غير الفارغة لا تتغير. الإقرار بـNeeds Attention لا يغير هذه الأهلية.

المستدعي يبقى مؤلف Message البشري الأصلي وبنطاق Lead وبالـCurrent Human Controller. هذه قاعدة حفظ هوية رسالة تاريخية؛ Manager يستطيع معالجة رسالته الخاصة بنفس المسار بعد takeover الموثق، ويستطيع قراءة سجل Agent ضمن فرعه، لكنه لا يستولي بصمت على رسالة Agent قديمة. إذا انتقل المتحكم/المالك، يبقى السجل القديم محفوظاً، وأي رسالة جديدة ينشئها المتحكم الجديد تمر عبر composer/policy بهويته الحالية؛ لا تتغير هوية الرسالة القديمة.

Recovery transaction تقفل Connection أولاً، ثم تعيد Lead ACL وتثبت Lead/Conversation وJob/Message، وتفحص النسخة/الأهلية والسياسة المركزية وAttachment READY ونفس snapshot للقالب المعتمد. لا Provider I/O فيها. سبب بين 10 و500 حرف إلزامي وrate limit عشرة طلبات في الدقيقة لكل replica/IP. تحفظ السجل وAudit وتزيد version وتعيد Job واحدة وMessage نفسها إلى QUEUED atomically؛ طلبان بالنسخة نفسها ينتجان نجاحاً واحداً وتعارضاً واحداً. أرقام المحاولات لا تصفّر: تزيد budget إلى `attempts + 5` كدورة تقنية bounded بطلب صريح، لا خمس رسائل Business جديدة. Worker الحالية تعيد السياسة قبل dispatch؛ تغيّر DNC بعد recovery يمنع الإرسال. لا تتجاوز recovery sender pinning أو health أو sending window أو consent أو template approval، ولا تمحو سبب مراجعة Conversation. الواجهة بالعربية/الفرنسية/الإنجليزية تعرض التاريخ والسبب وتأكيد إرسال نفس المحتوى، والأهلية الأولية لا تغني عن فحص POST/worker.

### Quick Reply templates وربط inbound

تقبل profile حتى3 أزرار QUICK_REPLY ذات labels ثابتة حتى25 حرفاً، دون CTA أو متغيرات label. create يرسل labels فقط وفق [مثال Meta الرسمي](https://www.postman.com/meta/whatsapp-business-platform/request/uzphwqw/create-template-w-text-header-text-body-text-footer-and-2-quick-reply-buttons). بعد approval/binding، ينشئ enqueue Message UUID قبل snapshot، ويولد لكل زر payload ذات nonce عشوائية128bit: `qr.messageId.index.nonce`. لا تقبل API payload من العميل. تحفظ snapshot tokens الأصلية؛ idempotency ترجع Message نفسها، وworker/recovery تتحقق من عددها ومفتاح Message/index والنسخة المعتمدة وتعيد استعمالها. adapter تبني indexed `button/quick_reply` مع parameter `payload` وفق [Meta Component Object](https://whatsapp.github.io/WhatsApp-Nodejs-SDK/api-reference/types/component_object/)؛ المرجع SDK مؤرشفة، والتحقق الحالي Mock وليس Live Meta.

الوارد `type=button` يستخدم [شكل callback الرسمي](https://www.postman.com/meta/whatsapp-business-platform/request/5qal58f/received-callback-from-a-quick-reply-button-click). يفحص payload ثم Message PK وnonce/index/label التاريخية، وConnection/Sender/Participant وprovider context إن وُجد؛ يربط Conversation المصدر نفسها حتى مع عدة Conversations نشطة ولا يستعمل label لاختيار Lead. لا يقرأ source بـFOR SHARE قبل قفل Conversation، لتجنب ترتيب قفل عكسي؛ المحتوى التاريخي immutable. reference بلا Provider ID بعد سباق reply/ACK تبقى Pending Review ويمكن حسمها ضمن المصدر نفسه بعد وصول ACK. unknown/forged/mismatched/closed لا تتجاوز الربط بواسطة اختيار Lead يدوي؛ تحفظ Needs Attention ويمكن للمسؤول المصرح فحص النص المحدود أو تجاهلها بسبب. لا يتحول reply فاسد إلى inbound TEXT عامة.

Migration039 تضيف `reply_to_message_id` و`reply_button_index` وFK/index وقيود الاتجاه/المؤلف/النوع/نفس Conversation/Connection/Sender والlabel التاريخية وحماية immutable. Migration040 تصلح قبول NULL بسبب SQL CHECK بثلاث قيم عبر اشتراط index غير فارغة صراحة، دون تعديل migration039 بعد تطبيقها. رد الزر لا يغير Consent/DNC/Controller/Lead ولا ينفذ workflow أو يرسل جواباً تلقائياً. Message API/Audit لا تعرض raw tokens أو snapshot؛ الواجهة تعرض labels كنص غير تفاعلي وreply link/index ضمن Lead ACL الحالية، بما فيها reassignment. operational test-send تستبعد Quick Reply لأنها خارج Conversation context؛ الإرسال عبر Conversation هو المسار المدعوم.

dynamic URL تستخدم `urlExample` للاحقة مثال الاعتماد، يحولها adapter إلى `example:[renderedUrl]`، و`templateUrlParameter` للقيمة عند الإرسال؛ لا تستعير HEADER/BODY value ولا approval example. parser لا تسمح بمتغير داخل authority أو بموضع غير نهائي/متعدد؛ render يفحص origin الثابتة والطول والـpercent/control/backslash ورفض full URI كلاحقة. snapshot تحفظ URL template وقيمة suffix المستقلة؛ Message API تعيد الهدف التاريخي rendered من snapshot وحدها. Worker/recovery تقارن القالب canonical كاملة بما فيها ترتيب الأزرار، وتستخرج index الأصلية من القالب المعتمد؛ adapter ترسل button/sub_type=url/index/parameters:text بالقيمة فقط وفق [Meta Button Parameter Object](https://whatsapp.github.io/WhatsApp-Nodejs-SDK/api-reference/types/button_parameter_object/) و[Meta Component Object](https://whatsapp.github.io/WhatsApp-Nodejs-SDK/api-reference/types/component_object/). SDK مؤرشفة ومرجع components الحديث لدى Meta عاد429؛ هذه مراجع الشكل واختبارات mock، وليست Live Verification أو ادعاء سعة المزود الحالية. operational test-send ترفض URL المتغيرة حتى إن كانت BODY ثابتة. أمثلة الاعتماد لا تدخل immutable snapshot/Agent API/Audit؛ تغير المثال وحده لا يعطل النسخة المعنوية.

تعريف الأهداف ثابت في القالب المعتمد لدى Meta، والإرسال يستخدم الاسم/اللغة وHEADER/BODY parameters اللازمة. Message.body تحتفظ بالنص المعروض، وtemplate_snapshot تحتفظ بالأزرار وأهدافها؛ Message list تعيد templateButtons مشتقة من snapshot التاريخية بعد ACL، دون raw snapshot أو أمثلة المزود. UI تعرض الرابط/رقم الاتصال في preview والتاريخ مع React escaping وHTTPS/tel validation وnoopener/noreferrer؛ تغير Catalog لاحق لا يغير هدف Message السابقة. تغير label/target قبل dispatch أو recovery يمنعها بـTEMPLATE_CHANGED حتى لو لم يتغير Message.body. JSON الحالية وimmutable trigger كافيتان دون migration جديدة.

اختبار integration الطويل يستخدم عناوين loopback اصطناعية منفصلة لمجموعات validation؛ المحاولات السلبية السابقة استهلكت quota إنشاء القوالب20/15 دقيقة بحق. حد rate limit في التطبيق محفوظ، ولا يستعمل production entrypoint تحكم الاختبار أو تجاوزاً للحد.

TEXT HEADER variable تستخدم `headerExample` في create للمراجعة و`templateHeaderParameter` في send؛ كلتاهما منفصلة عن BODY examples/parameters. parser تقبل {{1}} مرة واحدة فقط ولا تقبل {{2}} أو تكرارها أو FOOTER variables. `renderTextHeader` تتحقق من المثال والقيمة والنص النهائي حتى60 حرفاً، قبل provider I/O. adapter create تضيف `example.header_text`، وsend تبني header text parameter مستقلة عن body component، وفق بنية components في [SDK Meta الرسمي](https://github.com/WhatsApp/WhatsApp-Nodejs-SDK/blob/main/website/docs/api-reference/messages/template.md) و[مرجع Templates](https://www.postman.com/meta/whatsapp-business-platform/folder/lczy75a/templates). لا تعد fakes تحققاً من قبول Meta لهذه الطلبات؛ Live Verification ما زالت معلقة.

`headerParameter` تضاف إلى immutable snapshot فقط عند استعمالها، وتدخل مقارنة idempotency وإعادة فحص worker/recovery. static/BODY-only snapshots القديمة لا تتغير. Available Templates ترجع components نصية canonical بلا provider examples كي تعرض الواجهة preview صحيحة بقيم HEADER/BODY مستقلة؛ لا تستخدم استبدال {{1}} في النص المركب كله بالقيمة نفسها. operational test-send تتطلب headerParameterCount=0 وBODY count=0، وليس BODY ثابتة وحدها. UI Catalog تتحمل null/text-object من مزود غير موثوق وتعرض Unsupported format دون تفسير object كـReact content أو تعطيل الصفحة.

`parseTextTemplate` تحلل BODY المطلوبة وHEADER TEXT/FOOTER الاختياريين بترتيب ثابت؛ لا تتجاهل component غير مدعومة أو مكررة. creation وcatalog metadata وCampaign binding/available وenqueue/worker/recovery وoperational test-send تستخدم القاعدة نفسها. BODY تقبل المتغيرات المتسلسلة السابقة؛ FOOTER ثابتة بلا placeholders؛ HEADER تسمح {{1}} مرة واحدة مع مثال وقيمة مستقلين عن BODY، بحد تقني محافظ 60 حرفاً لكل منهما وBODY1024، منفصل عن Business sending limits. بنية المكونات وفق [نموذج Meta الرسمي](https://www.postman.com/meta/whatsapp-business-platform/request/uzphwqw/create-template-w-text-header-text-body-text-footer-and-2-quick-reply-buttons)؛ Buttons مدعومة ضمن profiles الموثقة أعلاه، والحدود هنا validation profile للتنفيذ المدعوم وليست إعلاناً عن جميع قدرات المزود.

Snapshot التاريخية تحفظ المكونات النصية كلها وقيم BODY؛ Message.body تحتوي النص النهائي كاملاً. أمثلة اعتماد المزود لا تدخل Snapshot ولا Available Templates المرسلة إلى Agent. Worker/recovery يعيدان فحص التطابق والاعتماد والربط قبل إرسال اسم/لغة القالب وقيم BODY عبر adapter؛ تبدل HEADER أو FOOTER يمنع الإرسال مثل تبدل BODY. لا migration جديدة: JSON components وقيود immutable الحالية تغطي هذا التوسع. القوالب القديمة ذات BODY واحدة تحافظ على شكل snapshot السابق.

Catalog pagination تقرأ صفحة SQL محدودة ثم تحلل المكونات؛ cursor تتقدم بآخر صف SQL حتى لو كانت الصفحة المرئية فارغة بسبب format غير مدعومة، ولا تقرأ قائمة غير محدودة لتملأ الصفحة. أصلح فحص SQL القديم الذي كان يخفي BODY متغيرة من صفحة Campaign رغم أن binding تقبلها. operational test-send UI تعتمد supported/parameterCount من Backend؛ لا تعيد اختراع parser خاصة بالواجهة. helper HTTP يضيف Content-Type JSON فقط عند إرسال body نصية، ويحتفظ بترويسة صريحة للأنواع الأخرى؛ طلبات sync/logout بلا body لا ترسل JSON فارغة إلى Fastify. أسماء selects صريحة لضمان accessibility بعد تغير خيارات القالب.

Playwright CLI على Windows قد تنهي العملية صراحة بعد global teardown؛ `fetch` هناك أظهرت محلياً assertion libuv حتى بعد نجاح الاختبارات. teardown الآن تستخدم `node:http` مع `agent=false/Connection:close` وtimeout، وتستهلك response قبل إنهاء cleanup؛ API/DB تغلقان طبيعيًا. هذا يعالج مسار الاختبار دون إخفاء exit code أو تعديل runtime النظام. [تقرير Undici upstream](https://github.com/nodejs/undici/issues/5680) يصف race مماثلة مع fetch وprocess.exit على Node24/Windows؛ نسبة العطل لها استنتاج من الأعراض والتحقق المحلي، وليست تشخيصاً عاماً لكل libuv assertion.

`test:e2e` يبني Backend والواجهة ثم يشغل Playwright بworker واحدة على server اختبار مستقلة تحت `test-e2e`، وbuild الواجهة نفسها فوق Fastify origin loopback دون API route mocking. server ترفض غير قاعدة `lead_operations_test` المحلية أو غياب `E2E_RESET_TEST_DATABASE=1` أو production، قبل إنشاء اتصال أو truncate؛ لذلك لا تشغلها بالتوازي مع integration/benchmark. الحسابات وpassword والتشفير/test-control token عشوائية أو fixtures اصطناعية فقط. control endpoints مقتصرة على entrypoint الاختبار وتحميها token سرية وOrigin، وتستدعي Worker والخدمات الحقيقية مع provider fake؛ لا تستوردها `src/server.ts` أو `src/app.ts`. fixture وtrace/screenshots تحت `.local/e2e` ولا تدخل Git. Playwright تطلق Browser context جديدة مؤقتة دون persistent profile؛ يمكن اختيار `E2E_BROWSER_CHANNEL=msedge` أو `chrome` المثبتين، والافتراضي Chromium للاختبار/CI. Native forced process.exit أثناء cleanup سبب assertion Windows محلياً؛ teardown تغلق server وPostgreSQL طبيعياً ثم تنتهي العملية.

التحقق المحلي على Edge يشمل Human text dispatch/recovery/history والتحكم/DNC/UNKNOWN/assignment ACL وCustomer escaping وArabic RTL/mobile وFrench/English، وليس كل UI أو Meta live. تحديث Conversation عند عرض الرسائل وبعد رفض send يمنع استعمال snapshot قديمة عند takeover التالية، وcomposer لا تعرض لغير Current Human Controller؛ backend يفحص tab قديمة أيضاً. المراجع التقنية لـharness: [Playwright webServer](https://playwright.dev/docs/test-webserver)، [Browser channels](https://playwright.dev/docs/browsers)، [Assertions](https://playwright.dev/docs/test-assertions).

Unit tests للقواعد، API integration tests مع PostgreSQL، اختبارات permissions ومحاولات URL مباشرة، سيناريوهات webhook/idempotency/out-of-order، simulations للـAI، E2E UI، migration smoke، واختبار حمل لمسارات intake/message. اختبار mock لا يساوي تحققاً مباشراً من Provider. أي Connection بلا credentials حقيقية تعرض حالة غير متصلة ولا تُسجل نجاحاً وهمياً.
