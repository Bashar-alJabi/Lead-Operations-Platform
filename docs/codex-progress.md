## آخر حالة مستقرة: قوالب Messaging النصية ذات متغيرات BODY

بعد checkpoint `fc3930f` أصبح إنشاء قالب `BODY` يحوي placeholders متسلسلة `{{1}}` إلى `{{10}}` متاحاً من داخل واجهة الإدارة مع أمثلة نصية لطلب اعتماد Meta؛ يمكن كذلك مزامنة قالب معتمد من المزود. يتحقق Backend من ترقيم المتغيرات وتسلسلها وأمثلتها قبل إنشاء الطلب ويحفظ النتيجة عبر مسار idempotent نفسه. قائمة Conversation تعرض القوالب النصية المعتمدة والمربوطة بالحملة وعدد قيمها، ويُدخل المتحكم البشري القيم من الواجهة. خدمة outbound المركزية تتحقق من العدد والمحتوى وصلاحية الوصول والـController والسياسة والربط، وتثبت النص الناتج والقيم ونسخة BODY الأصلية داخل Message التاريخية. مفتاح idempotency نفسه لا يقبل قيماً أخرى. Worker يعيد فحص اعتماد القالب وربطه وتطابق BODY والنص/القيم، ثم يرسل `body.parameters` إلى Meta adapter؛ تغيّر القالب بعد Queue يمنع Provider call ويضع `TEMPLATE_CHANGED` للمراجعة. لا Migration جديدة لأن `template_snapshot` التاريخية تستوعب البيانات، ورسائل القوالب الثابتة القديمة تبقى قابلة للإرسال. Header/Buttons/Media وTemplate formats الأخرى غير مدعومة في هذا المسار.

التحقق: migrations `001`–`029` على PostgreSQL Docker التطوير والاختبار؛ 23/23 unit و8/8 integration على PostgreSQL، وBackend/Web typecheck وWeb build ناجحة. Fake Meta adapter يفحص شكل create `example.body_text` وشكل send `body.parameters`. API integration يغطي إنشاء قالب متغير ورفض أمثلة ناقصة/ترقيم غير متسلسل، عرض العدد ضمن النطاق المصرح، رفض قيم ناقصة، idempotency والقيم المختلفة، Snapshot غير قابلة للتعديل، Worker send، ومنع الإرسال بعد تعديل القالب. لا UI E2E أو Meta sandbox/live أو اختبار اعتماد فعلي من Meta.

قيد التنفيذ التالي: بعد حفظ ورفع هذا checkpoint، تابع Messaging وفق وثيقة القبول، بدءاً بمرفقات Conversation والوارد media/attachment وحماية التخزين والتحميل والتحقق من النوع والحجم والـcapability، ثم استرداد Dead-letter/نتيجة الإرسال الملتبسة وقياس throughput. أكمل Meta intake ثم Payments/Enrollment ثم AI؛ لا تصف Messaging بأنها كاملة قبل ذلك.

## آخر حالة مستقرة: Messaging provider backpressure وصحة الطابور

بعد checkpoint `b92055d` أضيفت migration `029_messaging_backpressure.sql` لحالة `cooldown_until` على Connection وSender وآخر رمز خطأ مختصر وفهرس Jobs المستحقة. عند رد مزود صريح `429` يحفظ Worker فترة انتظار مستمدة من `Retry-After` مع سقف تقني للمحاولة، ويوقف التقاط كل رسائل الاتصال والمرسل حتى انتهاء الفترة، بما فيها الرسائل الأخرى المعلقة. فحص الجاهزية يتكرر قبل `PREPARED` لحماية السباق بين التقاط Job وتغير الاتصال؛ إعادة الطابور حينها لا تستهلك محاولة ولا تضع رسالة Customer في `FAILED`. كذلك تبقى Jobs المعلقة عند تعطيل الاتصال أو انتهاء اعتماده، وتُراجع قواعد Consent/Controller/Template مجدداً حين يعود الاتصال. محاولة `RUNNING` منتهية وبدأت Provider call تُوسم `UNKNOWN` حتى إن كان الاتصال معطلاً، ولا تعاد تلقائياً. رد `401/403` يحوّل الاتصال إلى `AUTH_EXPIRED` وصحة أرقامه إلى `UNKNOWN` حتى إعادة تهيئته. المسار التشغيلي test-send يحترم cooldown، ويصنف `429` رفضاً مؤكداً مع نتيجة idempotent قابلة للمراجعة. API وواجهة الإدارة تعرضان حالة cooldown ورمز الخطأ وعمق الطابور وعمر أقدم رسالة؛ Manager يرى عدد فرعه فقط في الاتصال المشترك وAgent ممنوع. لا توجد حدود throughput ثابتة مخترعة؛ تبقى جودة الرقم المكتشفة إشارة تشغيلية.

التحقق: PostgreSQL Docker `healthy`؛ migrations `001`–`029` على قاعدتي التطوير والاختبار؛ 22/22 unit و8/8 integration على PostgreSQL وBackend/Web typecheck وWeb build ناجحة. تغطي الاختبارات `429` مع رسالة ثانية لا تُرسل، عزل إحصاءات فرعين على اتصال مشترك، تعطيل الاتصال دون فقد Job أو استهلاك محاولة، استرداد محاولة `PREPARED` قديمة كـ`UNKNOWN` أثناء التعطيل، انتهاء اعتماد المزود مع بقاء رسالة أخرى معلقة واستئنافها بعد استعادة مصطنعة، و`429` في test-send مع replay بلا إرسال إضافي. لا اختبار UI E2E أو load أو Meta sandbox/live. التزامن بين عدة Senders على Connection واحدة لم يُختبر حملياً بعد.

قيد التنفيذ التالي: بعد حفظ ورفع هذا checkpoint، راجع متطلبات Messaging المتبقية في `docs/06-final-completeness-and-acceptance.md`، ثم نفّذ المرفقات الواردة والصادرة مع فحص نوع/حجم الملف وتخزين آمن وقرار capability لدى المزود، أو جزّئها إلى checkpoint ثابت قبل القوالب المتغيرة وHandoff/Recovery. لا تعلن Messaging مكتملًا قبل اختبار كل مساراته، ولا تنتقل إلى AI قبل Meta intake وPayments/Enrollment حسب ترتيب الاعتماديات.

## آخر حالة مستقرة: inbound text resolution ومراجعة الأحداث

بعد checkpoint `0e51a97` أضيفت migration `028_inbound_review.sql` لملاحظات قرار المراجعة وفهرس أحداث inbound المنتظرة. عامل Messaging يعالج أحداث `INBOUND_MESSAGE` الموقعة والمحفوظة سابقاً في دفعات محدودة. يربطها بمرجع رسالة سابقة (`context.id`) إن كان صالحاً، ثم Conversation نشطة ذات Connection/Sender/participant مطابق، ثم Contact/Lead مفتوحة مع Campaign sender override أو Branch default أو shared fallback مصرح به. لا يختار بين عدة Conversations أو Leads متطابقة، ولا يعيد فتح Conversation مغلقة أو ينقل Pinned Sender تلقائياً. عند تطابق وحيد يحفظ Message واردة تاريخياً برقم المزود ويحدّث وقت المحادثة، دون رد تلقائي. طلبان واردان متزامنان للـLead نفسها لا ينشئان محادثتين. إذا كانت AI Controller، تتحول الحالة إلى `AI_HANDOFF_REQUIRED` بلا إرسال AI.

الحالات الملتبسة أو غير المدعومة تبقى `NEEDS_ATTENTION`. API وواجهة المراجعة يعرضان نص الرسالة ومرشحي Lead/Conversation بعد فحص صلاحية Super Admin أو Manager لاتصال فرعه؛ Agent والفرع الآخر ممنوعان، وManager لا يراجع اتصال Organization مشتركاً. يختار المستخدم هدف الربط صراحة أو يتجاهل الحدث بسبب مدقق مع إبقائه محفوظاً؛ قفل الحدث وقيد Provider Message ID يمنع التكرار عند الحسم المتزامن. اختلاف `context.id` مع هدف يدوي مرفوض. محادثة جديدة دون Agent مؤهل تبدأ `WAITING_FOR_HUMAN/NO_HUMAN_CONTROLLER`، ويمكن لمستخدم مصرح له توليها بإجراء versioned مع Handoff history وAudit. Content من العميل يُعرض كنص React غير موثوق. رسائل media/attachments تبقى محفوظة كأحداث `INBOUND_CONTENT_UNSUPPORTED` للمراجعة ولا تُدّعى معالجتها، ولا توجد مطابقة حاسمة لمرجع حملة/إعلان خارجي بعد.

التحقق: migrations `001`–`028` على قاعدتي التطوير والاختبار عبر PostgreSQL Docker؛ 22/22 unit و8/8 integration على PostgreSQL، وBackend/Web typecheck وWeb build ناجحة. اختبار Webhook الموقّع يغطي الربط بمحادثة قائمة، وContext reference، وLead وحيدة، والغموض بين Leadين، ومرشحين لا يتسربون عبر الأدوار/الفروع، والحسم المتزامن وidempotency، وفتح محادثة واحدة من حدثين متزامنين، ورفض Sender معطّل، وmedia غير مدعومة، والتجاهل المدقق، وتولّي Manager للمحادثة ورفض Agent/الفرع الآخر وتعارض version. لا UI E2E أو Meta sandbox/live.

قيد التنفيذ التالي: لا تغييرات غير محفوظة بعد حفظ هذا checkpoint. الخطوة الدقيقة: مراجعة Messaging مقابل `docs/06-final-completeness-and-acceptance.md` وسد فجوات تشغيلية لازمة قبل إعلانه end-to-end، بدءاً بـprovider capabilities/health/throughput والـhandoff/recovery ومرفقات الرسائل والقوالب غير الثابتة عند الحاجة، ثم اختبارات الفشل والأداء وواجهة المراقبة. استمر إلى Meta intake ثم Payments/Enrollment ثم AI وفق dependency order؛ لا تنقل Messaging إلى Complete قبل تحقق شروط 06.
